设计第 1 部分：架构与数据流

AI 汇总作为 Homepage 内的独立全宽组件；密钥、原始数据和模型调用全部停留在服务端。

① 数据来源复用当前四个经营模块的数据接口，不让浏览器重新拼装数据。
📦出荷出力今日输出、配送、店铺分布、数据新鲜度
🧾运营对应待处理订单、咨询、低分评价和来源状态
💴乐天销售实时销售、7日趋势、店铺与商品 Top 信号
📈经营表现访问、UU、同星期中位数、新客/复购结构
② 服务端分析先做可靠的数据处理，再交给 GPT 负责解释和行动建议。
并发采集

四组接口独立超时；一个来源失败不会拖垮全部。

归一化与脱敏

删除身份、订单号、联系方式和链接；评价只保留脱敏摘要。

→
确定性指标层

计算环比、基准差、严重度和证据键，防止模型发明数字。

→
Responses API

自定义 URL / Key / model，reasoning.effort = xhigh，一次返回日中双语。

③ 校验与存储模型输出不是直接显示；必须通过结构和证据校验。
结构化输出校验
  • 状态、结论、依据、行动均有固定字段
  • 依据引用 metricKey，实际数字由程序渲染
  • 日文和中文在同一份结果内一一对应
持久化快照
  • 原子写入 config/uo-ai-summary.json
  • 保留最新结果与最近 24 个小时级紧凑快照
  • 不持久化评价原文，仅保存脱敏后的分析输入
④ 触发与展示自动调度与手动重算共用同一条受控分析链路。
每小时自动生成服务启动时恢复缓存；缺失或过期则补算，之后按小时执行。
手动重新分析POST 触发，10 分钟冷却；并发请求合并，避免重复计费。
顶部全宽卡片默认日文；中文原位切换。浏览器只获取已校验的摘要。
