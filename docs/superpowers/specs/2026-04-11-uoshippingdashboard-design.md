# uoshippingdashboard 改版设计（2026-04-11）

## 背景

当前 `src/widgets/uoshippingdashboard/component.jsx` 已经具备完整的数据展示能力，但在 homepage 中作为首页主视觉组件时，仍存在以下问题：

- 标题、更新时间、summary、detail 同时争抢注意力，第一视觉焦点不够明确。
- 顶部 4 张 summary 卡与下方 4 个 detail panel 的视觉权重接近，层级不够清晰。
- `明日予定` 与 `今日出荷` 在大多数时间为 0 / 空状态，现有大尺寸空面板会造成明显的空间浪费，并打断扫读路径。
- 当前组件更像“完整业务看板”，但还不够像 homepage 上的“主视觉核心模块”。

本次设计目标是在不脱离 homepage 现有暖色主题的前提下，让该组件更具首页核心感，同时保持桌面近距离查看时的可读性与稳定性。

---

## 已确认的设计结论

### 1. 顶部采用一体式 Hero Header

顶部不再使用“标题栏 + 4 张独立 summary 卡”的结构，而是改为一个完整的 Hero 区块，统一承载：

- 图标
- 标题
- 更新时间
- 刷新按钮
- KPI 区

Hero Header 应承担首页主视觉身份，成为组件的第一锚点。

### 2. 顶部与下方顺序统一

为避免用户上下跳读，顶部 KPI 与下方 detail panel 顺序统一为：

1. 今日出力
2. 昨日出荷
3. 今日出荷
4. 明日予定

### 3. 主次分化

顶部 Hero 中只保留一个主 KPI：

- **主 KPI：今日出力**

其余 3 个作为辅助 KPI：

- 昨日出荷
- 今日出荷
- 明日予定

主 KPI 需要在体量、数字大小、视觉聚焦上明显强于其它 3 个辅助 KPI。

### 4. 常空面板采用“轻量空卡”

`今日出荷` 与 `明日予定` 在多数时间为空，因此：

- 保留四栏结构，不做动态坍塌。
- 空状态不再使用大面积虚线空盒子。
- 改成更轻、更短、更像状态卡的空态表现。
- 当二者为空时，位置固定在后两列。

### 5. Detail 区采用“有数据优先”的扫读顺序

下方四个 panel 的顺序确定为：

1. 今日出力
2. 昨日出荷
3. 今日出荷
4. 明日予定

原因：

- 第一屏先看到最常有内容的两块。
- 两个常空卡自然沉到后面。
- 更符合 homepage 主视觉模块的阅读路径。

---

## 设计目标

### 目标

- 让组件更像 homepage 的首页主视觉模块，而不是普通业务卡片集合。
- 明确阅读顺序：模块身份 → 核心数字 → 明细内容。
- 优化常空状态，使其不再制造“大片无效区域”。
- 保持日语界面文案与现有业务语境一致。
- 保持四栏总体结构稳定，避免因为有无数据而频繁改变大布局。

### 非目标

- 不改变 homepage 的全局暖色主题。
- 不引入新的交互流程或复杂筛选器。
- 不重构 API 数据结构。
- 不把四块业务数据彻底改成不对称布局（例如只保留一块主卡 + 其它完全从属卡）。

---

## 最终视觉结构

## 1. Hero Header

Hero Header 分为两层：

### 第一层：身份层

左侧：
- icon（放入独立小容器）
- 标题 `出荷出力-リアルタイム`

右侧：
- 更新时间 `更新時刻`
- 刷新按钮 `更新`

设计原则：
- 标题是主信息。
- 更新时间是次信息。
- 刷新按钮使用轻量 ghost button 风格，不抢视觉重心。

### 第二层：KPI 层

顺序：
1. 今日出力（主 KPI）
2. 昨日出荷
3. 今日出荷
4. 明日予定

设计原则：
- `今日出力` 体量更大，数字字号最大。
- 其它 3 个 KPI 风格统一，但权重低于主 KPI。
- 不再依赖 4 种不同边框色来表达差异。
- 主要依靠体量、字重、透明度与布局差异建立主次。

---

## 2. Detail Grid

下方保留四栏 detail grid，但整体视觉权重降低，作为内容层承接具体数据。

### 顺序

1. 今日出力
2. 昨日出荷
3. 今日出荷
4. 明日予定

### 设计原则

- panel 比 Hero 更轻。
- panel 背景、边框、阴影都应弱于 Hero。
- 列表项更像数据条目，而不是厚重卡片堆叠。
- badge 保留，但做轻量化处理。

---

## 空状态策略

## 1. 空状态适用范围

重点应用于：

- 今日出荷
- 明日予定

这两个 panel 多数时间会为空，因此其空态需要被设计为“正常状态的一部分”，而不是异常提醒。

## 2. 空状态表现

采用轻量空卡：

- 保留 panel 标题。
- 内部使用更小尺寸的状态卡。
- 视觉上明显轻于有数据状态。
- 不使用居中大虚线框占据大面积空间。

### 推荐空态文案（日语）

#### 今日出荷为空
- `本日の出荷はまだありません`
- 辅助文案可选：`更新を待機中`

#### 明日予定为空
- `明日の予定はまだありません`
- 辅助文案可选：`次回更新で反映されます`

说明：
- 文案应表达“当前正常但暂无内容”，而不是错误、失败或缺失。
- 新文案必须通过 i18n key 管理，不直接写死在 JSX 中。

---

## 文案与语言要求

本次改版所有面向用户的界面文案均以日语为准。

### 已有文案继续保留
- `更新時刻`
- `更新`
- `今日出力`
- `昨日出荷`
- `今日出荷`
- `明日予定`

### 建议新增 i18n key

- `uoshippingdashboard.noTodayShippingYet`
- `uoshippingdashboard.noTomorrowScheduleYet`
- `uoshippingdashboard.waitingForUpdate`
- `uoshippingdashboard.willAppearNextRefresh`

## 组件映射到现有代码的调整方式

当前文件：`src/widgets/uoshippingdashboard/component.jsx`

### 可继续保留的部分

- `normalizeShops`
- `normalizeCouriers`
- `CategoryTabs`
- `filterItemsByCategory`
- `getCategoryTotals`
- `resolveActiveCategory`
- `formatNumber`
- `useWidgetAPI` 数据获取逻辑
- `Panel` 的基础抽象（可调整样式与头部结构）

### 需要替换或重构的部分

#### 1. `SummaryCard`
当前 `SummaryCard` 为 4 张并列摘要卡。

应替换为：
- `HeroHeader`
- `HeroPrimaryKpi`
- `HeroSecondaryKpi`

#### 2. 顶部更新时间工具条
当前顶部更新时间行应并入 `HeroHeader`，不再作为独立一行存在。

#### 3. `EmptyState`
当前空状态组件偏通用，但视觉上更适合完整空面板。

建议拆分为：
- `EmptyState`：保留给普通空态
- `CompactEmptyState`：用于 `今日出荷` / `明日予定` 的轻量空卡

#### 4. sections 顺序
当前 `dashboard.sections` 由 output + shipping 直接拼接。

应改为显式顺序：
- `today-output`
- `yesterday-shipping`
- `today-shipping`
- `tomorrow-output`

#### 5. summary 顺序
当前 summary 顺序是：
- 今日出力
- 明日予定
- 今日出荷
- 昨日出荷

应改为：
- 今日出力
- 昨日出荷
- 今日出荷
- 明日予定

## 状态与交互规则

### 分类 tabs

`今日出力` 的分类 tabs 保留。

规则：
- 仅在当前 section 真的存在多个 category 时显示。
- 若 section 为空，不应保留大面积空 tabs 区域。
- 对常空区（今日出荷 / 明日予定）不需要增加额外 tabs 或复杂控制。

### 刷新交互

- 刷新入口整合进 Hero Header。
- 交互保持当前 `mutate()` 方式不变。
- 按钮视觉降级为辅助操作，不与主 KPI 争焦点。

### 加载与错误状态

- loading skeleton 需与新 Hero 结构匹配。
- error 状态仍沿用 `Container` 的错误处理逻辑。

## 验证场景

改版后至少验证以下 4 类界面状态：

### 场景 1：最常见状态
- 今日出力：有数据
- 昨日出荷：有数据
- 今日出荷：空
- 明日予定：空

### 场景 2：四块都有数据
- 验证整体权重是否仍然正确。
- 验证后两块即使有数据，也不会压过前两块的阅读顺序。

### 场景 3：仅一块为空
- 例如今日出荷为空、明日予定有数据。
- 验证单个轻量空卡不会破坏整体平衡。

### 场景 4：高密度列表
- 今日出力店铺较多
- 昨日出荷配送项较多
- 验证滚动区域与面板高度是否协调

---

## 实现原则

- 优先复用现有数据处理逻辑，不额外引入复杂状态管理。
- 以结构重组 + className 体系调整为主。
- 顶部 Hero 属于必须改结构的部分。
- Detail panel 优先做权重下调，而非彻底重做。
- 空状态必须以“正常但暂无内容”的语气表达。
- 所有新增 UI 文案必须接入 i18n。

---

## 最终结论

本次 `uoshippingdashboard` 改版的最终方向为：

- 顶部采用 **D：一体式 Hero Header**。
- 下方 detail 顺序采用 **B：有数据优先**。
- `今日出荷` 与 `明日予定` 采用 **轻量空卡** 方案。
- 顶部与下方顺序统一为：
  - 今日出力
  - 昨日出荷
  - 今日出荷
  - 明日予定
- 所有界面文案使用日语。

该方案兼顾了：
- 首页主视觉存在感
- 桌面场景可读性
- 空状态长期稳定性
- 当前业务结构的连续性
